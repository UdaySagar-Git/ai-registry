# Grok Build evidence

Every path, variable, detection signal, file format and command in `src/targets/grok.ts` is a claim, and each has a row here. A claim counts only when one of these settles it:

1. the target's official documentation: the exact sentence, its URL and the date it was read;
2. the target's public source, where the documentation is silent: repository, file, line and commit;
3. a real install of the target: the command run, the target version and its output.

A claim no source settles is left out of the definition and recorded as undocumented. The definition, its JSON twin in `test/fixtures/targets/grok.json` and `grok.test.ts` match this file exactly.

Every page below was read on 2026-10-29, as the Markdown copy the site serves at the URL given (`https://docs.x.ai/build/...md`; the site's own index is `https://docs.x.ai/llms.txt`). Source lines are in https://github.com/xai-org/grok-build at commit `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8` ("Synced from monorepo", 2026-09-29), whose crates are version `1.0.45` (`crates/codegen/xai-grok-version/Cargo.toml:4`, `crates/codegen/xai-grok-pager-bin/Cargo.toml:3`) and whose `SOURCE_REV` is `559751fdcec02d413e4c57c8832ab275e4f44980`; every source path below is under `crates/codegen/`. ## L2 probes

The target's own command that lists what aireg placed, and what it printed. `grok.test.ts` runs it after installing the fixtures in the project and in the user scope, with `GROK_HOME` set to `<sandbox>/.grok` and `GROK_DISABLE_AUTOUPDATER=1`; Grok Build 1.0.5 passed both. The output below is the same command run by hand after `aireg add acme/engineering --all --for grok`, in the project and with `-g`, from `examples/acme-registry`.

- `grok inspect --json`, from the home folder (https://docs.x.ai/build/cli/reference.md, "Show the configuration Grok discovers for this directory"). It needs no account. Abridged to the user's own skills and agents:
  ```json
  {"skills": [{"name": "pr-review", "source": {"type": "project", "path": "<sandbox>/home/.grok/skills/pr-review/SKILL.md"}}],
   "agents": [{"name": "reviewer", "source": {"type": "project", "path": "<sandbox>/home/.grok/agents/reviewer.md"}}]}
  ```
  From the home folder Grok walks `~/.grok` as the current folder's, so it labels the user folders `project`.
- `grok inspect --json`, from the project, which nothing trusts:
  ```json
  {"projectTrusted": false,
   "skills": [{"name": "pr-review", "source": {"type": "project", "path": "<sandbox>/home/project/.grok/skills/pr-review/SKILL.md"}}],
   "agents": [{"name": "reviewer", "source": {"type": "project", "path": "<sandbox>/home/project/.grok/agents/reviewer.md"}}]}
  ```
  1.0.5 lists the project skill although the folder is untrusted; the 1.0.45 source would leave it out, so the probe checks only the project agent, which both load.

## Left out

- **`plugin` as a Grok plugin.** Grok loads a folder in `~/.grok/plugins/<name>/` with a `plugin.json` (or `.claude-plugin/plugin.json`), but at 1.0.45 a user plugin starts disabled until `[plugins] enabled` in `$GROK_HOME/config.toml` names it, which the docs contradict, and a plugin's agents are spawned by the qualified name `<plugin>:<agent>`. A `register` entry appending `{name}` to `["plugins", "enabled"]` would express it, but nothing here was run, so a namespace lands as its parts (`shape: "contents"`) until an install settles the enable step.
- **`claude-code` in `reads`.** Grok reads `.claude/skills` and `~/.claude/skills` by default, but only while `[compat.claude] skills` and `GROK_CLAUDE_SKILLS_ENABLED` stay on, and always at `<home>/.claude`, never at `CLAUDE_CONFIG_DIR`. A skill aireg leaves in Claude Code's folder alone could vanish for Grok, so the definition reads only its own folder and the shared one. Grok's recursive walk also finds the `skills/<name>/SKILL.md` inside a Claude plugin aireg places under `.claude/skills/<plugin>/`, and its `commands/*.md`.
- **`.agents` before `.grok` for skills.** Both are read in both scopes and the user `~/.agents` does not move with `GROK_HOME`, so either order works; `.grok` comes first because the docs confirm it in both scopes, while project `.agents/skills` rests on 1.0.45 source alone.
- **`restrictions` on agents.** Grok honours `tools` and `disallowedTools`, but a `tools` entry it does not know (not a Grok tool, not a mapped Claude tool, not `mcp__*`) makes it keep the whole toolset, so an agent limited by a tool another target names can run in Grok with every tool. No codec expresses "refuse unknown tool names", so this is reported for review, not handled.
- **Agent keys of the wrong type.** A Claude Code key Grok also types (`permissionMode`, `maxTurns`, `effort`, `isolation`, `memory`) with a value Grok rejects fails the whole file. Claude Code's documented values parse; `model: sonnet` parses as an override to a model id Grok may not have, which was not run.
- **Version and verified range.** `verified.range` is 1.0.5, the release installed and probed; the source rows are at 1.0.45, and the current 1.0.70 was not run.
- **MCP.** Not a kind here; noted for later: "Grok also loads MCP configurations from `~/.claude.json`, `.cursor/mcp.json`, and project `.mcp.json` files, merged below `config.toml` in priority." (https://docs.x.ai/build/features/mcp-servers.md).
